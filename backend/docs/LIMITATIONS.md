# Alice Backend — Known limitations and caveats

A living file. After every working run, add a **Run log** entry at the bottom (what was built, what was verified, what was not) and update the **Open items** table (add new rows, change status, never silently delete). We revisit this file as we build.

Status values: `open`, `partial`, `mitigated`, `resolved`, `accepted` (known and deliberately left).

| L30 | Commands | Confirmation tolerances absorb HA rounding (brightness ±1%, colour ±4, colour temperature ±60 K, target temperature ±0.5, cover position ±2, fan speed ±34). | L31 | Commands | No per-entity queueing. Concurrent commands on one entity race, and one state change can satisfy both (confirmation is by desired state, by design). | Ambiguous attribution under contention | Serialize per entity if it matters in practice | accepted | Run 5 |
| L32 | Commands | `timed_out` does not cancel anything in HA; the device may still change later. `actualState` is only a snapshot at timeout. | A "timed out" command can succeed afterwards | Late-confirmation note on the command, or keep watching briefly | open | Run 5 |
| L33 | Commands | Scenes, scripts and `stop` have no observable state, so they confirm when HA accepts; the effect is not verified. | L34 | Commands | `device_unavailable` fails fast from the cached availability, so a stale cache can reject a device that just came back. | Rare spurious failure | Resync-check before failing | accepted | Run 5 |
| L35 | Commands | `failure.message` can carry HA's raw error text. Command events carry the full command, including parameters. | Internal details could reach clients | Sanitize at the API; filter `/ws` command events by permission | open | Run 5 |
| L36 | IDs | ULIDs are time-ordered only to the millisecond. Both command stores break same-ms ties by insertion order (rowid in SQLite). | L37 | Auth | Public auth endpoints are rate limited per client (30/min); invitation and recovery code guessing is capped at 10 per 15 min per client and 100/hour overall (Run 8). Responses are 429 with `Retry-After`. See L48 for what this does not cover. | Online guessing is bounded | See L48 | mitigated | Run 7 |
| L38 | Auth | Sessions have a fixed expiry (no sliding renewal) and no device naming. `Secure` cookie only when `NODE_ENV=production`. No CSRF token: protection is `SameSite=Lax` plus JSON-only bodies. Removing a passkey does not revoke other sessions. | Long-lived stolen cookie stays valid until expiry/revoke | Sliding expiry, revoke-all on credential change, double-submit CSRF token if cross-site embedding is ever needed | open | Run 7 |
| L39 | Auth | Passkey attestation is `none` and not checked (no AAGUID allow-list). Login asks for user verification as "preferred", step-up requires it. | A non-biometric authenticator can sign in (but cannot step up) | Require UV for login too if policy demands | accepted | Run 7 |
| L40 | Auth | Tested only with a software authenticator. Real browsers/phones, RP ID and origin in production, and **Capacitor** (WebView origin, Android asset links / iOS associated domains, a native passkey plugin) are untested. | Passkeys may not work in the wrapped app without extra setup | Spike on real devices before building the mobile shell | open | Run 7 |
| L41 | Auth | Recovery codes are the only recovery path (10 one-time codes, shown once). | L42 | Households | One household per user: `getMembership` returns the earliest membership; users cannot join a second household or switch. The old `memberships` stub module was folded into `households`. | No multi-household yet | Multi-household support later (schema is ready) | accepted | Run 7 |
| L43 | Permissions | The Devices API filters by `evaluateDeviceAccess` (Run 8): guests see only devices with an allow, denied devices are removed, hidden/forbidden things are 404, and entities a person may not see are pruned from the Things they do see. | L44 | Permissions | Sensitivity rules match on (domain, action, device_class) only: no per-device or per-role rules. | Cannot say "only guests need step-up for this lock" | Add scope columns if needed | accepted | Run 7 |
| L45 | API | Built in Run 8: HA connection setup (`/ha/connection*`), `/devices`, `/devices/:id`, capabilities, rename/hide/merge/split, `/entities/:id/role`, `/areas`, `/commands`. Not built: `/ws` realtime, `/devices/:id/activity`, `PATCH /devices/:id/settings` (power limit, voice exposure), favorites, groups, scenes, routines, automations, modes. | No push updates; remaining modules are stubs | Next: realtime, then groups/favorites/scenes | partial | Run 7 |
| L46 | Audit | Audit rows are written (auth, membership, policy, sensitivity changes) but there is no read endpoint (`/admin/audit`) and no retention policy. | Cannot review the log through the app | `GET /admin/audit` with pagination | open | Run 7 |
| L47 | Persistence | The initial migration was regenerated from scratch in Run 7 (no deployed database existed). Migrations are append-only from now on. SQLite file backup is not scheduled yet. | None now | Keep migrations append-only; backup job with the Backups module | accepted | Run 7 |
| L48 | Rate limiting | Limits are per process, in memory (reset on restart), keyed by client IP only: no per-account lockout, and a fixed window allows a burst at each boundary. `TRUST_PROXY` must match the deployment, or the IP is the proxy's (everyone shares a limit) or spoofable. Only `/auth/*` is limited: commands, device and admin endpoints are not. | A determined attacker can spread guesses across IPs within the global cap; heavy clients are not throttled | Shared store if several instances run; per-account lockout; limits on commands and admin routes | open | Run 8 |
| L49 | HA connection | One connection per household is enforced by the service, not by a database constraint. `PUT /ha/connection` makes this server connect to an admin-supplied URL (http/https only, credentials and link-local addresses refused; LAN and loopback allowed on purpose). A saved connection that cannot start returns 502 but stays saved. The stored `status` is updated from events only, so it can be stale after a crash (live status is read from the manager). | SSRF surface is limited to admins with step-up | Allow-list of hosts if the deployment needs it; unique index when multi-connection arrives | accepted | Run 8 |
| L50 | Things API | Visibility is per entity. A Thing's name, area and `hubThingId` are shown to anyone who can see at least one of its entities, so a hub's id can be revealed to a guest who cannot open the hub. Hide, merge, split and rename are household-wide, not per person. | Minor information exposure; no per-user views | Strip `hubThingId` when the hub is invisible; per-user nicknames if wanted | open | Run 8 |
| L51 | Things API | There is no "unmerge" endpoint: a merge can only be undone by splitting its entities out. `thing_links` rows accumulate (merges and splits are never deleted), and merging Things from different HA connections is refused. | Stale link rows; clumsy undo | `DELETE` for links; compaction | open | Run 8 |
| L52 | Commands API | `POST /devices/:id/commands` has no idempotency key, so a double tap or retry runs twice (harmless for turn_on, not for toggle). Command results are polled until `/ws` exists. | Possible duplicate effects on retry | Idempotency-Key header; `/ws` | open | Run 8 |
| L53 | API | Not built yet: favorites, per-device settings (`power limit`, `voice exposure`), `/devices/:id/activity`, command undo. The `Thing` response has no favorite flag. | UI features that need them have no endpoint | With the favorites/activity/energy modules | open | Run 8 |
| L54 | Testing | The fake Home Assistant in e2e tests reacts instantly and only to turn_on/turn_off/lock/unlock; the live HTTP test depends on the mock HA's current state (it picks targets that differ from the current value). Neither covers slow devices, partial failures or HA restarts. | Timing and failure behaviour only tested at executor level | Add a controllable-delay fake and a restart test | open | Run 8 |

## Run log

### Run 1 — HA module (committed `e19c688`)
- Built: gateway interface, WebSocket gateway, connection manager (backoff + jitter, no retry on bad token, resync after reconnect), discovery/inventory, state cache, capability detector, event normalizer, in-process bus, `core/` restructure.
- Verified: 32 unit tests and 3 integration tests against the mock HA, typecheck clean.
- Not verified / not built: see L04–L11, L14, L25, L26.

### Run 2 — Capability-aware state normalizer (committed in `e19c688`)
- Built: `normalizeState`, `normalized` on events and cached entities.
- Verified: unit tests including brightness round-trip (1–100%), live test (30% set, observed 30%).
- Caveats recorded: L12, L13.

### Run 3 — Things model (committed `637406d`)
- Built: registry field extension, role classifier, name cleaner, grouping (`buildThings`) with overrides, fixtures incl. an Echo-style ESPHome device.
- Verified: 64 tests passing; live run over the mock HA's 128 entities produced 115 Things (97 visible).
- Found and fixed: integration test depended on the light's starting brightness (L23).
- Caveats recorded: L15–L24.

### Run 4 — Facet values (committed `637406d`)
- Built: `facet-values.ts` (`describeFacet`, `describeThingFacets`): polarity from `device_class` (fixed HA semantics), then name tokens, then user override `onMeans`; unknown/unavailable never guessed; `deviceClass` added to `ThingEntity`.
- Verified: 49 tests in `things/` (device-class table, name-token cases, "unmuted" is not "muted", ambiguity reporting, override and derived opposite, enum sensors, unavailable states, Echo example end to end).
- Result for the Echo example: with no polarity information the shutter facet is `ambiguous` (On/Off) rather than wrongly labelled; once `onMeans: "closed"` is set it reads Closed/Open. A fully automatic answer is not possible from HA data alone (L01).
- Caveats recorded: L01–L03.

### Run 5 — Command executor (uncommitted when written)
- Built: `CommandExecutor` (validate, authorize, step-up for sensitive operations, dispatch, accept, desired-state confirmation, timeout, cancel), expectations with tolerances and parameter validation, in-memory store, allow-all authorizer, `command.*` events on the bus, `resolveThingTarget`, ULID ids.
- Verified: 29 new unit tests (fake gateway: happy paths, already-true, unobservable, physical-press confirmation, unrelated change times out, late confirmation, HA rejection, pre-dispatch failures, household scoping, denied/step-up, cancel) plus 6 live tests against the mock HA (switch on/off, toggle, brightness in percent, step-up unlock/lock of a real demo lock, HA-rejected value, event order). Live tests passed twice in a row.
- Fixed in passing: finished runs were kept in memory forever; now dropped once settled. A flaky ordering test exposed that same-millisecond commands could list in the wrong order; the store now breaks ties by insertion order (L36).
- Caveats recorded: L08 (now partial), L27–L36.

### Run 6 — Plan update: configurable sensitive operations (docs only)
- Decision (from the user): admins can choose which device operations need step-up, with lock `unlock` and `open` as defaults. Recorded in ARCHITECTURE.md (security model, build order step 4), DATABASE.md (`sensitive_operation_rules`) and API.md (`/admin/security/sensitive-operations`). To be built with the permissions module; the executor will take a `SensitivityPolicy` in place of the fixed `isSensitiveOperation`.
- Caveats: L29 updated. Not built or tested yet.

### Run 7 — Identity, households, permissions, HTTP layer (uncommitted when written)
- Built: database foundation (schema for identity, households, access, commands, audit; fresh migration; `createDb`/`createTestDb`; `DrizzleCommandStore`), passkey auth (register, login, step-up, add passkey, recovery codes, restricted recovery sessions, DB sessions with hashed tokens), households (first-user bootstrap, invitations, members, last-admin guard, expiring guests), permissions (role matrix, device policies, DB authorizer, admin-configurable sensitivity policy replacing the fixed list), session plugin and guards, and the HTTP routes under `/api/v1` for auth, users, household, permissions and `/admin/security/sensitive-operations`. API prefix moved from `/api` to `/api/v1`. `buildApp(services)` replaces the app singleton.
- Verified: 183 tests (the whole suite, including 33 for auth and HTTP). WebAuthn registration, login and step-up run through the real `@simplewebauthn/server` verification with a software authenticator (wrong origin, replayed challenge, other user's passkey, missing user verification are all refused). End-to-end HTTP flows: register, cookie flags, logout, invitations, role limits, step-up renewal, recovery, policy and sensitivity settings. Booted the real server against a fresh SQLite file: migrations apply, `/health`, `/docs` and a registration challenge respond.
- Hardened along the way: step-up now requires user verification (device presence alone is not enough).
- Caveats recorded: L04, L05, L06, L27, L29, L36 updated; L37–L47 added.

### Run 8 — Devices, commands, HA connection setup, rate limiting (uncommitted when written)
- Built: rate limiter and `enforce()` on `/auth/*` (per client and global caps for code guessing, 429 + Retry-After, `TRUST_PROXY`); AES-256-GCM secrets; migration `0001` (`ha_connections`, `thing_overrides`, `entity_overrides`, `thing_links`); `HaConnectionService` and `/ha/connection` endpoints (test, save, admin token, resync, remove, restore at boot); `ThingsService` (build per household, cache, overrides from the database, rename/hide/merge/split/entity role); `presentThing` (live values, facet meaning, per-caller pruning); `DevicesService` and routes for devices, entities, commands and areas; `CommandExecutor` wired with the database store, authorizer and sensitivity policy; interrupted-command recovery and graceful shutdown at boot.
- Verified: 220 tests passing (new: rate limiter, secrets, 23 e2e tests over HTTP with a fake HA covering connection setup, Things, overrides, commands, step-up and who-sees-what, and 3 tests of the whole stack over HTTP against the mock HA, run twice). Test logging is silent via `bunfig.toml`.
- Caveats recorded: L03, L04, L07, L08, L22, L27, L37, L43, L45 updated; L48–L54 added.
